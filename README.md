# День 25. Мини-чат с RAG и памятью задачи

Веб-чат на Python 3.11 и Streamlit: несколько диалогов, поиск по документам при каждом новом сообщении, ответы с проверяемыми цитатами и постоянная память задачи. После перезапуска можно продолжить разговор с прежней целью и ограничениями.

## Возможности

- Создание и переключение диалогов, сохранение полной истории в SQLite.
- Память цели, уточнений, ограничений, терминов, решений и открытых вопросов.
- Замена требований с сохранением происхождения и истории изменений.
- Переписывание follow-up вопросов в самостоятельные поисковые запросы.
- Локальные embeddings E5, векторный поиск и cross-encoder reranking.
- Источники, раскрываемые точные цитаты, диагностика поиска и памяти.
- Отдельные статусы недостаточного контекста и технической ошибки.
- Повтор запроса без дубликатов, последовательная обработка внутри диалога.

## Установка

Нужен **Python 3.11**. Команды для PowerShell:

```powershell
git clone https://github.com/MariaAgafonova/advent-day-25-rag-memory.git
cd advent-day-25-rag-memory
py -3.11 -m venv .venv
.\.venv\Scripts\python.exe -m pip install torch==2.6.0 --index-url https://download.pytorch.org/whl/cpu
.\.venv\Scripts\python.exe -m pip install -e ".[dev,corpus]"
Copy-Item .env.example .env
```

Укажите в локальном `.env` или окружении процесса `LLM_API_KEY`, `LLM_BASE_URL` и `LLM_MODEL` для провайдера с API Chat Completions. Проверки с реальной моделью выполнялись с DeepSeek. Файл `.env` исключён из Git; шаблон не содержит секретов.

Дополнительные настройки клиента: `LLM_TIMEOUT_SECONDS`, `LLM_TEMPERATURE`, `LLM_MAX_OUTPUT_TOKENS`, `LLM_CONTEXT_WINDOW_TOKENS`, `LLM_OUTPUT_TOKEN_PARAMETER`, `LLM_THINKING`, `RAG_MAX_CONTEXT_TOKENS`. Поддерживаются алиасы `DEEPSEEK_*` из `.env.example`. Приоритет имеет окружение процесса.

## Подготовка базы знаний

Загрузите демонстрационный корпус официальной Android-документации и создайте индекс:

```powershell
.\.venv\Scripts\python.exe scripts/download_corpus.py
.\.venv\Scripts\python.exe -m document_indexer index --input data/raw --strategy structural --output output/structural.sqlite
```

Корпус включает Activity lifecycle, Fragment lifecycle, ViewModel, coroutines, WorkManager, deep links и архитектуру. URL и атрибуция находятся в `data/sources.json`. Скрипт сохраняет уже существующие файлы. При первой индексации загружается `intfloat/multilingual-e5-small`; при первом поиске с reranking — `cross-encoder/mmarco-mMiniLMv2-L12-H384-v1`.

Для собственных документов поместите Markdown, TXT или текстовые PDF в `data/raw` и повторите индексацию. Также доступны страницы документов и индексации в интерфейсе. Дополнительный индекс с фиксированным разбиением создаётся той же командой с `--strategy fixed --output output/fixed.sqlite`.

Документы, готовые индексы и личная история не включены в репозиторий. Отдельный синтетический корпус `data/day25_test_corpus` предназначен только для mock-проверок.

## Запуск и работа с чатом

```powershell
.\start.ps1
```

Откройте **http://127.0.0.1:8505**. Альтернативная команда запуска:

```powershell
.\.venv\Scripts\python.exe -m streamlit run ui/app.py --server.port 8505 --server.address 127.0.0.1
```

На странице «Мини-чат» создайте диалог или выберите существующий. Отправьте вопрос, затем уточнение — например, «А второй вариант?». Под каждым ответом доступны источники, цитаты и «Диагностика retrieval» с исходным и переписанным запросами, scores, отобранными чанками, версией памяти и временем этапов.

Панель «Память задачи» показывает цель, уточнения, ограничения, термины, решения, открытые вопросы и ревизии. Действие «Сбросить память» и команда `/reset` очищают память только текущего диалога, сохраняя историю. Сообщения до сброса остаются для просмотра, но не возвращают забытые требования в контекст.

При ошибке обновления памяти сохраняются сообщение и последнее корректное состояние. Продолжение блокируется до повтора проблемного сообщения или сброса. Повтор использует прежний `request_id` и не дублирует сообщения.

## Архитектура

| Данные | Хранение | Назначение |
|---|---|---|
| База знаний | `data/raw`, `output/structural.sqlite` | Документы, чанки, метаданные и embeddings — основание фактов |
| История | `output/chat.sqlite` | Полные сообщения, время, статусы, источники и диагностика |
| Память задачи | `task_states` и ревизии в `chat.sqlite` | Цель и актуальные требования конкретного диалога |

История и память помогают понять запрос, но не являются доказательствами фактов и автоматически не индексируются. Каждый диалог имеет собственный `conversation_id`.

Обработка сообщения: сохранение → валидируемое JSON-обновление памяти → самостоятельный поисковый запрос → retrieval → reranking/фильтрация → ограниченный контекст → генерация → проверка цитат → сохранение ответа. Retrieval выполняется и для уточнений; повтор завершённого `request_id` возвращает сохранённый результат.

Модули `chat_storage.py`, `chat_memory.py` и `chat.py` отвечают за хранение, память и обработку сообщений. В основе RAG — загрузчики, chunkers, E5, NumPy search, `process_candidates`, `ContextBuilder`, `ChatCompletionsClient` и `EvidenceValidator`. Интерфейс находится в `ui/views/chat.py`.

Элементы памяти содержат сообщение-основание, происхождение `user_explicit` / `inferred` и актуальность. Новое явное требование заменяет прежнее с сохранением истории; предположение не может перезаписать явное ограничение. Ответ ассистента не считается принятым решением пользователя.

## Контекст и настройки

Модели передаются память, краткое резюме, последние N сообщений и целые найденные чанки. Полная история остаётся в SQLite. При сокращении контекста сохраняются активные цель и ограничения; если обязательный контекст не помещается, возвращается ошибка.

Настройки `CHAT_*` задаются **в окружении процесса**, например `$env:CHAT_RECENT_MESSAGES = "8"` перед запуском:

| Переменная | По умолчанию |
|---|---|
| `CHAT_INDEX` | `output/structural.sqlite` |
| `CHAT_RECENT_MESSAGES` | `8` |
| `CHAT_MAX_MESSAGE_CHARS` | `4000` |
| `CHAT_HISTORY_BUDGET` | `2500` |
| `CHAT_CONTEXT_WINDOW` | `20000` |
| `CHAT_OUTPUT_TOKENS` | `1800` |
| `CHAT_DOCUMENT_BUDGET` | `6000` |
| `CHAT_RETRIEVAL_MODE` | `reranker` (также доступен `filter`) |
| `CHAT_QUERY_LANGUAGE` | `en` (либо `original`) |
| `CHAT_SIMILARITY_THRESHOLD` | `0.85`, только для cosine-фильтра |

Поиск по английскому корпусу использует английский запрос; ответ и память сохраняют язык пользователя. Reranker отбирает 5 из 15 кандидатов. Cosine-порог не применяется к logits реранкера и требует калибровки для своего корпуса. Счётчик контекста использует известный tokenizer, иначе консервативное число UTF-8 байтов; это не точное измерение токенов каждой модели. Размер окна должен соответствовать провайдеру.

## Источники и недостаточный контекст

Ответ всегда содержит `status`, `answer` и `sources`. Статусы: `answered`, `partial`, `insufficient_context`, `clarification`, `error`. Подтверждение изменения памяти может иметь статус `clarification` без документальных утверждений.

Валидатор проверяет, что `chunk_id` найден в текущем retrieval, чанк прошёл фильтрацию, `source` и `section` совпадают с метаданными, а `quote` точно содержится в тексте. Инструкции внутри документов считаются данными. Предыдущий ответ ассистента не используется как доказательство.

Без подтверждения ответ начинается с «Не знаю на основании доступных документов» и предлагает добавить подходящий документ. При неоднозначной ссылке чат задаёт уточняющий вопрос. Источники не придумываются: `sources = []`, интерфейс показывает «Источники: нет подтверждённых источников». Ошибка retrieval имеет статус `error`. Частично покрытый вопрос получает ответ только в подтверждённой части.

## Проверки

```powershell
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m document_indexer evaluate-day25 --mock
.\.venv\Scripts\python.exe -m document_indexer evaluate-day25 --live --index output/structural.sqlite
.\.venv\Scripts\python.exe scripts/verify_fragment_lifecycle.py --live
```

Mock не требует доступа к LLM и проверяет механику хранения, поиска, фильтрации и валидации с тестовыми моделями. Это не проверка качества реального RAG. Live использует настроенного провайдера, E5 и reranker; требуется подготовленный индекс.

Ожидания зафиксированы в `data/day25_scenarios.json`: **A — сохранение цели и ограничений**, **B — изменение требований и слабый контекст**. Каждый сценарий содержит 12 пользовательских сообщений. Можно выбрать `--scenario A` или `--scenario B`. Отчёты создаются в `output/day25_evaluations/`: сообщения, ответы, источники, память каждого шага, запросы, ожидания, фактический результат и pass/fail. Для live отдельно оценивается смысловая поддержка ответа цитатами.

Перед публикацией: **187 passed, 3 deselected**. Оба сценария ранее прошли 12/12 с mock и 12/12 с реальной моделью; дополнительная реальная проверка Fragment lifecycle — 5/5. Длинные live-сценарии после добавления Fragment повторно не запускались. Даты, состав прогонов и ограничения — в [отчёте дня 25](DAY25_RESULTS.md) и [отчёте Fragment lifecycle](FRAGMENT_FIX_RESULTS.md).

Точное совпадение цитаты не доказывает смысловую поддержку утверждения. Семантическая LLM-оценка не заменяет независимую ручную экспертизу. Приложение предназначено для локального учебного использования; авторизация и нагрузочное тестирование не входят в реализацию. Личные диалоги, `.env`, индексы и подробные локальные отчёты исключены из Git.
